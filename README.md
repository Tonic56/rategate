# rategate

![CI](https://github.com/Tonic56/rategate/actions/workflows/ci.yml/badge.svg)

Rate limiter на Go по алгоритму token bucket, в памяти процесса, без
зависимостей за пределами стандартной библиотеки.

Лимитер держит по одному ведру на ключ (IP, идентификатор пользователя, API
токен), пополняет его с постоянной скоростью и на каждый запрос отвечает
тремя вещами: разрешён ли запрос, сколько токенов осталось и через сколько
клиенту можно повторить попытку.

**Статус: в разработке.** Ядро готово, покрыто тестами и измерено; дальше —
HTTP middleware и сервис с REST/gRPC API (см. [Планы](#планы)). Пакет пока
лежит в `internal/`, потому что вопрос, выходит ли rategate ещё и как
подключаемая библиотека, пока не решён.

## Почему token bucket

Ведро вмещает до `limit` токенов и получает `rate` токенов в секунду. Каждый
запрос забирает `cost` токенов; если их не хватает, запрос отклоняется.

* Короткие всплески разрешены (у клиента, который молчал, ведро полное), при
  этом средняя скорость на длинном интервале остаётся равной `rate` запросов
  в секунду.
* В отличие от fixed window, на границе окна нет двойного всплеска: счётчик
  не обнуляется в начале каждой минуты, токены возвращаются непрерывно.
* Состояние одного ключа — два числа: количество токенов и время последнего
  пополнения. На каждый запрос ничего хранить не нужно, в отличие от
  sliding window log.
* Токены не доливает фоновый таймер: `Check` сам считает
  `tokens += elapsed * rate` от времени последнего пополнения и обрезает
  результат по `limit`. Ни горутин, ни тикеров на ключ нет, поэтому миллион
  спящих ключей не стоит ничего, кроме памяти.

## Использование

Лимитер создаётся один раз при старте сервиса:

```go
// Ведро на 100 токенов, пополнение — 10 токенов в секунду.
l, err := limiter.NewTokenBucket(100, 10)
if err != nil {
	log.Fatal(err)
}

// Освобождать вёдра ключей, которые перестали приходить. Не обязательно:
// без Run лимитер работает, но память только растёт.
go l.Run(ctx)
```

И проверяется на каждый запрос, например в HTTP-хендлере:

```go
func (s *Server) handle(w http.ResponseWriter, r *http.Request) {
	// RemoteAddr имеет вид "IP:порт"; лимит считается по IP, а не по соединению.
	host, _, err := net.SplitHostPort(r.RemoteAddr)
	if err != nil {
		http.Error(w, "bad remote address", http.StatusBadRequest)
		return
	}

	req, err := limiter.NewRequest("ip:"+host, 1)
	if err != nil {
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}

	res, err := s.limiter.Check(r.Context(), req)
	if err != nil {
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}
	if !res.Allowed {
		retry := int(math.Ceil(res.RetryAfter.Seconds()))
		w.Header().Set("Retry-After", strconv.Itoa(retry))
		http.Error(w, "too many requests", http.StatusTooManyRequests)
		return
	}

	// обычная обработка запроса
}
```

Необязательные настройки передаются функциональными опциями, поэтому новые
настройки не ломают существующие вызовы:

```go
l, err := limiter.NewTokenBucket(100, 10, limiter.WithSweepInterval(30*time.Second))
```

Про некорректный вход лимитер сообщает sentinel-ошибками (`errors.Is`), а не
паникой: `ErrInvalidLimit`, `ErrInvalidRate`, `ErrInvalidRequest`,
`ErrCostExceedsLimit`, `ErrRefillTooSlow`, `ErrInvalidSweepInterval`.

## Решения в реализации

**Шардированное хранилище.** Вёдра лежат в 32 независимых мапах, у каждой свой
мьютекс; шард выбирается хешом ключа (FNV-1a). Запросы по разным ключам почти
никогда не ждут один и тот же лок — именно за счёт этого получаются
параллельные цифры ниже.

**Время читается под локом.** `Check` сначала берёт лок шарда и только потом
вызывает `clock.Now()`. Время, прочитанное до лока, может оказаться старше
`lastRefill`, который за это время записала другая горутина; если его
сохранить, `lastRefill` уедет назад, один и тот же интервал зальётся дважды и
лимитер выдаст лишние токены. Перенос чтения под лок попутно убрал второе
чтение: раньше время читалось до лока — только чтобы проинициализировать
новое ведро, — и ещё раз под локом, чтобы пополнить существующее. Один
`time.Now()` на вызов вместо двух ускорил `Check` с 108 нс до 67 нс (−38%,
p=0.000, n=8, по `benchstat`).

**Хранилище не знает ни про время, ни про токены.** Оно отдаёт ведро в колбэк
под локом и сообщает, был ли ключ новым; как стартует свежее ведро, решает
лимитер. Алгоритм остаётся в одном файле, а хранилище на Redis (фаза 4)
становится заменой только хранилища.

**Простаивающие вёдра удаляются обходом, а не TTL на каждый ключ.** `Run`
просыпается раз в интервал и выбрасывает вёдра, к которым не обращались
`limit/rate` секунд (но не меньше минуты). За такое время ведро уже полное,
поэтому клиент не отличит удалённое ведро от нового. Шарды блокируются по
одному, так что обход никогда не держит всё хранилище.

**Часы подменяемы.** Тесты используют фейковые часы и двигают их вручную,
поэтому пополнение, `RetryAfter` и чистка проверяются без `time.Sleep`.

## Бенчмарки

AMD Ryzen 7 7435HS (16 потоков), Go 1.27, Linux. `make bench`:

| Бенчмарк | нс/опер. | B/op | allocs/op |
| --- | --- | --- | --- |
| `Check`, одна горутина | 68–70 | 0 | 0 |
| `Check` параллельно, один общий ключ | 103 | 0 | 0 |
| `Check` параллельно, ключ на горутину | 9.0–9.4 | 0 | 0 |

В параллельных строках `ns/op` — это реальное время на операцию при занятых
всех 16 потоках, то есть мера пропускной способности: ~9.7 млн проверок/с,
когда все горутины бьются за одно ведро, и ~106 млн проверок/с, когда ключи
разложены по шардам. Строка с общим ключом — худший случай для такой
схемы: один мьютекс и 16 горутин в очереди к нему.

`Check` не аллоцирует ничего: ведро выделяется один раз на ключ, а `Result`
возвращается по значению.

Память, замер на 1 000 000 ключей (`BenchmarkMemoryPerKey`, живая куча после
принудительной сборки мусора):

| | байт на ключ |
| --- | --- |
| после 1 млн разных ключей | 103.8 |
| после чистки | 55.8 |

То есть миллион отслеживаемых ключей стоит примерно 104 МБ: само ведро — 32
байта (`float64` + `time.Time`), остальное — строка ключа и накладные расходы
мапы на запись, поэтому цифра растёт с длиной ключей. Те ~56 байт, что
остаются после чистки, — это память самой мапы: мапа в Go не сжимается при
удалении записей, освобождаются только структуры `bucket` и строки ключей.
Пересоздание почти пустой мапы шарда — в бэклоге.

## Тесты

```sh
make test   # go test -race ./...
make bench  # go test -run='^$' -bench=. -benchmem -count=5 ./...
make lint   # golangci-lint run
make cover  # отчёт о покрытии в браузере
make ci     # fmt, vet, lint, go fix -diff, test
```

Покрытие по строкам — 100%. Тесты проверяют конкурентные вызовы по одному
ключу и по разным ключам под `-race`, часы, идущие назад, комбинацию
`limit/rate`, при которой `RetryAfter` не влезает в `time.Duration`,
незаметность чистки для клиента, остановку `Run` по отмене контекста и каждую
sentinel-ошибку. `Run` тестируется через `testing/synctest`, который заодно
валит тест, если горутина утекла. CI гоняет те же цели на каждой ветке с
зафиксированными версиями инструментов.
